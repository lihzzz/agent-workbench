## 1. 结论摘要

当前本地项目在功能上基本是远端工作区的超集。两边应用版本号都为 `0.22.0-beta.2`，但本地增加了一个完整的新引擎、一套多引擎协作工作流，以及多项交互、性能和数据可靠性增强。

本地独有功能可以归纳为以下 10 组：

1. **完整的 OpenCode 第四引擎支持**：包括二进制检测、模型列表、会话生命周期、权限、流式事件、工具渲染、后台会话、恢复、标题生成和提交消息生成。
2. **Relay collaboration 多引擎接力协作**：把 Codex 与 Claude 会话组织为 Plan、Review、Fix、Implement、Code Review 等 Lane。
3. **可搜索、可点击回填的输入历史弹窗**：远端只有上下方向键召回。
4. **真正的长会话虚拟滚动**：远端采用分批渐进渲染，本地只挂载可见的历史行，并保留流式尾部的正常布局。
5. **日志体积治理和完整事件日志开关**：增加深度、字符串、数组、对象键和整行限制，默认不再写入完整高频事件。
6. **文件预览内直接编辑和保存**：Monaco 编辑模式、脏状态、快捷键保存，以及配套的文件写入 IPC。
7. **归档会话内容预览**：恢复或删除前可以查看消息、Markdown、Thinking 和工具调用。
8. **会话恢复与持久化可靠性增强**：启动恢复上次会话、卸载前刷新、延迟数据补水和原子文件写入。
9. **Checklist/Todo 兼容性与状态展示增强**：支持更多状态别名、可关闭面板，并正确区分“正在执行”和“已经停止但状态残留”。
10. **Codex 配置模型兜底显示**：读取 `config/read`，把配置中存在但 `model/list` 未返回的模型补进选择器。此项目前是本地未提交修改。

除上述功能外，本地还更新了应用图标资源和 OpenCode 实现计划文档；这些属于品牌资源和工程文档，不作为运行时功能展开。

## 4. OpenCode 第四引擎

OpenCode 是本地项目最大的独有功能。它不是一个简单的 Agent 注册项，而是贯穿主进程、预加载桥、渲染器状态机、会话持久化、工具渲染、模型设置和通知系统的一套完整引擎实现。

### 4.1 用户入口


### 4.3 主进程会话架构

本地采用“每个 Harnss 会话一个 `opencode serve` 进程”的隔离模型：

```text
Harnss Session
    |
    +-- 独立 opencode serve 子进程
    +-- 独立 localhost 端口
    +-- 独立 OpenCode SDK client
    +-- 独立 SSE 事件订阅循环
    +-- 独立 native opencodeSessionId
```

这样做的直接效果：

- 不同项目和会话的 cwd、模型和事件不会混在一起。
- 一个 OpenCode 会话退出时不会直接破坏其他 OpenCode 会话。
- Harnss 可以用自己的内部 session ID 管理 UI，同时持久化 OpenCode native session ID 用于恢复。

相关实现：

- `electron/src/ipc/opencode-sessions.ts`
- `electron/src/lib/opencode-client.ts`

### 4.5 启动、健康检查与事件重连

OpenCode server 启动时，本地会：

1. 申请一个空闲的 localhost 端口。
2. 执行 `opencode serve --hostname 127.0.0.1 --port <port>`。
3. 同时监听 stdout 的 listening 信息并轮询 HTTP 健康状态。
4. 20 秒内未就绪则终止启动。
5. 如果端口竞争导致 `EADDRINUSE`，允许重新分配端口重试。

事件订阅采用 SSE。连接意外结束但进程仍存活时会进行有界指数退避重连：

- 最大重连次数：3。
- 基础退避：250ms。
- 重连耗尽后结束该会话并向渲染器发送 `opencode:exit`，防止 UI 永久卡在 Processing。

### 4.6 模型发现与项目级过滤

本地通过 OpenCode `config.providers()` 获取 provider/model，并转为统一 ID：

```text
providerID/modelID
```

例如：

```text
anthropic/claude-sonnet-4-6
openai/gpt-5
```

之后读取以下配置位置，只保留用户实际配置的模型：

```text
<cwd>/opencode.json
<cwd>/.opencode.json
~/.config/opencode/opencode.json
~/.opencode/opencode.json
~/.opencode.json
```

支持配置字段：

- 顶层 `model`。
- `provider` 或 `providers`。
- provider 下 `models` 的 key。
- model 对象中的 `id` 或 `model`。

如果配置为空、损坏或过滤后没有任何匹配项，会回退到 OpenCode 返回的完整模型目录，避免配置解析失败把所有模型都隐藏。

模型会按项目 cwd 重新加载，并按引擎持久化到 `modelsByEngine.opencode`，避免不同项目的 OpenCode 配置互相污染。

## 5. Relay collaboration 多引擎接力

Relay collaboration 是本地第二个大型独有功能。它把原本互相独立的 Harnss 会话组织为一个共享项目 cwd 的多阶段协作链。

### 5.1 用户入口

本地侧边栏底部新增：

```text
Relay collaboration
```

点击后：

1. 如果当前项目已经存在 Relay group，重新打开该 group。
2. 如果不存在，则创建一个新的 Relay group 和第一个 Plan Lane。
3. 主工作区切换为横向 Lane 视图。

相关入口：

- `src/components/AppSidebar.tsx`
- `src/components/AppLayout.tsx`
- `src/hooks/app-layout/useAppEnvironmentState.ts`

### 5.2 默认协作配方

本地内置 5 个角色：

| 顺序 | Role | 默认引擎 | 主要输入 | 主要产物 |
|---:|---|---|---|---|
| 1 | Plan | Codex | 用户初始任务 | `PLAN.md` |
| 2 | Review Plan | Claude | `PLAN.md` + 上一阶段摘要 | `REVIEW.md` |
| 3 | Fix Plan | Codex | `PLAN.md` + `REVIEW.md` | 更新后的 `PLAN.md` |
| 4 | Implement | Codex | `PLAN.md` | 工作区代码修改 |
| 5 | Code Review | Claude | Git working tree + `PLAN.md` | 代码评审结论 |

配方定义在：

```text
src/lib/session/handoff.ts
```

### 5.3 Lane 模型

每一个阶段仍然是一个标准 Harnss session，而不是新造一套不可复用的会话协议。Lane 之间通过以下字段关联：

```text
workflowGroupId
workflowGroupName
stageRole
stageIndex
handoffFromSessionId
```

这些字段同时进入：

- ChatSession 类型。
- SessionMeta sidecar。
- 完整持久化 session JSON。
- 会话列表反序列化。

所以已 materialize 的 Relay Lane 可以随普通会话一起持久化和恢复。

### 5.4 Draft Lane 处理

Harnss 新会话在发送第一条消息前是 `DRAFT_ID`，尚未进入正式 `sessions[]`。Relay 为此维护 `pendingDraftLane`：

- 创建 Lane 后，UI 可以立即显示它。
- 第一条消息发送并 materialize 后，用 group ID + stage index 找到正式 session。
- 正式 session 出现后移除 pending draft。
- 聚合逻辑避免 draft 与刚 materialize 的 session 重复显示。

相关实现：

### 5.6 Handoff 交接

点击 Hand off 后：

1. 根据当前 role 推荐下一个 role。
2. 读取当前 Lane 最后一条非空 assistant 文本。
3. 如果当前 Lane 已不是活动会话，从磁盘/缓存加载 transcript 后提取最终文本。
4. 根据 role 模板生成建议 Prompt。
5. 用户可以更换目标 role。
6. 用户可以编辑完整 Prompt。
7. 用户显式确认后才创建下一 Lane 并发送。

Handoff 不会自动静默执行，符合“每阶段人工确认”的设计。

### 5.7 上下文传递方式

Relay 使用两条通道传递信息：

1. **共享工作区文件**：例如 `PLAN.md`、`REVIEW.md`。
2. **文本注入**：上一 Lane 最终 assistant 输出。

文本注入最多保留 4000 字符。超过限制时截断并添加：

```text
…(truncated)
```

模板支持：

```text
{prevRole}
{prevEngine}
{prevText}
{artifacts}
```

如果没有捕获到上一阶段输出，会使用明确占位文本，而不是生成结构损坏的 Prompt。

### 5.8 当前 Relay 边界

需要注意：

- 第一个 Plan Lane 创建后，初始任务由用户在 Relay Composer 中手动输入；当前代码不会自动套用 Plan role 的 `promptTemplate`。
- 后续阶段通过 Handoff Dialog 自动构造建议 Prompt。
- 默认配方固定在源码中，当前没有可视化配方编辑器。
- Group name 默认使用首个 role 名称；当前没有单独的 Rename UI。
- `handoffFromSessionId` 记录来源，但 UI 主要按 `stageIndex` 排序。
- Relay 视图打开时会占用主工作区，普通 Split View 和底部工具 Dock 暂时让位。

## 7. 长会话虚拟滚动

### 7.1 远端策略

远端采用渐进渲染：

- 初始只渲染底部约 20 行。
- 顶部历史先用一个估算高度 spacer 占位。
- 每个 animation frame 向上补约 40 行。
- 最终仍会把全部历史消息挂载进 DOM。

该策略改善首屏速度，但超长会话完全补水后 DOM 仍持续增长。

### 7.2 本地策略

本地在 `ChatView` 中使用 `@tanstack/react-virtual`：

- 历史区只渲染可见行和 overscan。
- overscan 为 12 行。
- 空闲状态保留最后 8 行为非虚拟化尾部。
- Processing 时保留当前 turn 和其上方 6 行缓冲为正常文档流。
- 流式消息、Thinking 展开、工具状态变化不受绝对定位历史区干扰。
- 通过真实 DOM 测量修正估算高度。
- 最多缓存 512 个行高，切换回来时减少视觉跳动。

### 7.3 行高估算

本地针对不同 row 类型提供独立估算：

- processing row
- turn summary
- tool group
- system/summary message
- user text + images
- assistant prose + thinking + code block
- ExitPlanMode 长计划

超长内容估算带上限，避免单个异常消息生成极端 spacer。

### 7.4 滚动行为

本地同时处理：

- 跳转到虚拟化历史消息时使用 `scrollToIndex`。
- 目标进入 DOM 后再进行精确居中。
- 用户主动向上滚动后停止自动锁底。
- 虚拟测量变化时，仅在用户从未主动滚动的情况下继续跟随底部。
- 工具组边界不会被虚拟/非虚拟区域切开。

相关实现：

- `src/components/ChatView.tsx`
- `src/lib/chat/virtualization.ts`
- `src/lib/chat/virtualization.test.ts`

## 11. 会话恢复与持久化可靠性

这组差异不一定表现为新按钮，但会直接影响“刷新后是否空白”“最后消息是否保存”“会话 JSON 是否损坏”。

### 11.1 冷启动/刷新恢复上次会话

本地在当前 Space 初始 mount 时：

1. 读取 `lastSessionBySpace`。
2. 等待 projects 和 sessions 数据加载。
3. 找到该 Space 上次活动 session。
4. 自动执行 `switchSession`。
5. 如果用户已经主动导航或正在 Draft，不覆盖用户选择。

远端只在 Space 发生切换时恢复 remembered session；冷启动或 `Cmd+R` 时 Space ID 没变，因此可能显示空白聊天。

实现：

```text
src/hooks/app-layout/useAppSpaceWorkflow.ts
```

### 11.2 初始消息延迟补水

恢复过程中可能出现：

```text
sessionId 已经设置
        ↓
磁盘 session payload 稍后才加载完成
```

远端 Engine Base 主要依赖 session ID 变化初始化。如果 ID 不再变化，后到的 `initialMessages` 可能无法进入空的 engine state。

本地增加同 session 延迟补水 effect：

- 只有 session ID 存在时运行。
- 只有后到消息非空时运行。
- 只有当前 messages 仍为空时运行。
- 同步恢复 processing、connected、sessionInfo、cost、context usage、model usage、compacting 和 permission。
- 不覆盖已经开始产生新消息的活动状态。

实现：

```text
src/hooks/useEngineBase.ts
```

### 11.3 页面卸载前刷新

现有自动保存有约 2 秒防抖。远端如果在最后消息到达后立刻刷新或关闭，最新消息可能尚未发往主进程。

本地监听：

```text
beforeunload
pagehide
```

事件触发时立即调用 `saveCurrentSession`。不会设置 `event.returnValue`，因此不会弹出浏览器式 Leave site 对话框。

实现：

```text
src/hooks/session/useSessionPersistence.ts
```

### 11.4 会话 JSON 原子写入

远端直接用 `fs.promises.writeFile` 覆盖：

- 主 session JSON。
- `.meta.json` sidecar。
- 元数据 patch。

本地改为：

1. 在同目录写唯一临时文件。
2. 完成后 `rename` 覆盖目标文件。
3. 失败时删除临时文件。

在 POSIX 同文件系统内 rename 是原子的，所以读者看到的要么是旧完整文件，要么是新完整文件，不会看到半个 JSON。

此功能特别防止：

- App 退出时 write 被中断。
- session JSON 截断后无法 `JSON.parse`。
- Sidebar 仍有 meta，但聊天无法打开、导出或删除的损坏状态。

实现：

```text
electron/src/ipc/sessions.ts
```

## 13. Codex 配置模型兜底显示

> 状态：本地当前未提交修改。  
> 文件：`electron/src/ipc/codex-sessions.ts`。

### 13.1 解决的问题

远端模型选择器完全依赖：

```text
model/list(includeHidden: false)
```

如果 Codex 配置文件显式设置了一个模型，但 app-server 的 `model/list` 没有返回它，远端会认为该模型不可用，并可能回退到其他模型。

### 13.2 本地行为

本地新增 `listCodexModelsWithConfiguredFallback`：

1. 正常调用 `model/list`。
2. 额外调用 `config/read`，按 cwd 读取配置。
3. 读取 `config.model`。
4. 如果该模型非空且不在 model/list 中，构造一个合成模型条目并插到列表首位。
5. `config/read` 失败时静默回退到原 model/list，不影响已有功能。

合成条目声明：

- display name 使用模型 ID。
- description 为 `Configured in Codex config.`。
- reasoning effort：`low`、`medium`、`high`、`xhigh`。
- 默认 effort：`medium`。
- input modality：text、image。

### 13.3 覆盖范围

此兜底同时用于：

- `codex:start` 启动时选模型。
- 存在活动 RPC 时的 `codex:list-models`。
- 无活动会话、临时启动 app-server 时的 `codex:list-models`。

### 13.4 风险

合成条目的能力元数据不是服务端真实返回值，而是本地假设。特别是：

- 该模型是否真的支持 `xhigh`。
- 是否支持 image。
- 默认 effort 是否应为 medium。
- 是否支持 personality。

正式合并前建议根据 `config/read` 或模型能力接口补充真实元数据，或者将未知字段标为保守值。

- Todo 状态归一化。
- 日志敏感字段清理、深度限制和长度截断。

仍建议补充或执行：

- OpenCode 与真实 provider 的端到端会话测试。
- OpenCode 权限 once/always/reject 的 UI 集成测试。
- OpenCode SSE 断线重连测试。

- Codex 自定义配置模型的真实 app-server 验证。

## 17. 合并回远端时的建议顺序

由于远端当前有 88 个未提交变更，不建议直接整目录覆盖。推荐按依赖顺序拆分迁移。

### 第一阶段：低耦合可靠性增强

1. 日志截断与 `logDebug`。
2. 单文件异步读取和 500KB 上限。
3. 会话原子写入。
4. beforeunload/pagehide 保存。
5. 初始 Space session 恢复。
6. Engine Base 延迟补水。
7. Todo 状态别名和停止状态显示。

这些功能相对独立，风险和冲突较小。

### 第二阶段：独立 UI 增强

1. 输入历史搜索弹窗。
2. 归档聊天预览。
3. 文件预览编辑。

文件编辑应先补足路径安全校验，再进入正式版本。

### 第三阶段：OpenCode 引擎

建议拆为：

1. shared types + dependency + tsup external。
2. binary/client/model filter。
3. Electron IPC + preload。
4. renderer adapter + hook。
5. Session Manager lifecycle。
6. settings/registry/icons/UI。
7. split/background/title/notification。
8. tests。

OpenCode 涉及 40 余个新增或修改文件，必须作为独立功能分支处理。

### 第四阶段：Relay collaboration

Relay 依赖稳定的 Session Manager、持久化和多 Pane 能力。推荐在 OpenCode 之后迁移，但默认配方本身只依赖 Codex 和 Claude，不强依赖 OpenCode。

迁移时应解决：

- Relay 入口与远端 PreRelease Banner 都位于侧边栏底部，不能简单互相替换。
- 初始 Plan Prompt 是否自动应用。
- Relay group 列表和重命名入口。
- 完成后的恢复入口。
- Lane 删除/重试/重新排序策略。
- Handoff 失败时 pending draft 的回滚。

### 第五阶段：Codex 配置模型兜底

因为它目前尚未提交且包含能力元数据假设，建议在真实 Codex app-server 上单独验证后再合并。

## 18. 最终判断

本地相对远端的核心价值不是零散 UI 改动，而是三层能力提升：

1. **引擎层**：增加 OpenCode，Harnss 从三引擎客户端扩展为四引擎客户端。
2. **工作流层**：增加 Relay，使多个单 Agent 会话可以围绕同一工作区形成明确的规划、评审、实现链路。
3. **产品可靠性层**：虚拟滚动、日志治理、原子写入、退出保存、冷启动恢复和延迟补水共同改善长会话与桌面应用长期运行体验。

如果目标是把本地能力完整迁移到远端，优先级建议为：

```text
数据可靠性
  > 日志与长会话性能
  > 输入历史/归档/文件体验
  > OpenCode
  > Relay
  > Codex 配置模型兜底
```

其中 OpenCode 和 Relay 是需要产品验收的大功能；其余可靠性和交互增强更适合先拆分合并。

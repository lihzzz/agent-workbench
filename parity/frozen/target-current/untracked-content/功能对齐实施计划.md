## 1. 目标

以**冻结后的源工作区实际内容快照**为唯一行为基准，`1.md` 只作为功能索引，不作为源码缺失时的替代实现规范。直接修改当前项目中所有不一致实现。当前 88 个未提交变更不享有优先保留权：行为已一致的代码可继续使用，行为不一致的代码直接修改或替换。

本计划的“功能一致”指：

1. 用户可见能力一致。
2. 会话生命周期、后台会话、分屏和持久化行为一致。
3. 现有 session JSON 保持向后兼容，新字段均为可选字段。
4. macOS、Windows 和 Linux 的二进制查找、文件写入与打包不回归。
5. 当前 88 个变更逐项对照源行为，不一致项必须修改，不得因“已有本地改动”而保留差异。
6. 默认入口、功能开关、设置默认值、迁移逻辑、IPC contract、错误状态和失败恢复行为一致。
7. 会话退出后子进程、事件订阅、权限请求、临时目录和监听器的资源状态一致且无泄漏。
8. parity ledger 中不存在未关闭、未解释或仅靠人工口头确认的差异。

“严格一致”不等于文件逐字相同，但要求同一输入、同一持久化数据和同一外部依赖状态下，两边产生等价的用户可见结果、IPC 结果和持久化结果。

## 2. 非目标

- 不追求两个工作区字节级一致。
- 不以整目录覆盖代替功能验证；具体文件若与源行为不一致，可直接修改或替换。
- 不在本轮扩展 OpenCode 自动安装、独立登录、Compact 或 Plan Mode。
- 不在本轮实现 Relay 可视化配方编辑器。
- 不把源工作区中尚未验证的 Codex 模型能力元数据直接当作事实。
- 不把只在目标工作区实施的安全增强、失败恢复或新 UI 当作“已经对齐”；这类增强必须同步应用到两边后才能关闭一致性项。
- 不要求应用图标、实现计划文档等非运行时资产完全一致，除非它们影响安装、启动、打包或用户可见行为。
- 不允许用永久 Developer Preview 开关掩盖最终行为差异；临时开关只能用于集成过程。

## 4. 集成原则

1. 以冻结的源工作区实际功能行为为唯一基准，目标工作区是主要修改落点。
2. `both-modified` 文件按功能行为对照；本地实现与源行为冲突时，以源行为为准直接修改，不为保留本地差异而折中。
3. 每个工作包使用独立 commit，可单独回滚。
4. 每个任务必须标记为 `P` 或 `H`：`P`（Parity）严格复刻冻结源行为；`H`（Hardening）超出冻结源行为，必须以同一 patch 同步应用到源、目标两边并重新冻结基线。
5. OpenCode 和 Relay 在集成期间可以临时放在 Developer Preview 开关之后；最终对齐验收前，开关默认值和入口可见性必须与源一致，或在两边同时采用同一开关和同一默认值。
6. `pnpm-lock.yaml` 通过相同 pnpm 版本重新生成，不直接复制源工作区 lockfile；生成后比较依赖图而不是只比较文本。
7. 所有持久化变更先加向后兼容读取，再开始写入新字段。
8. 首先解决数据安全与主进程阻塞，再引入新引擎和工作流。
9. `target-only` 的用户可见行为默认视为不一致，应删除、禁用或作为 `H` 同步到两边；只有源、目标默认行为一致时才标记为已对齐。
10. 对齐期间禁止源工作区无记录漂移；确需修复源实现时，必须先形成 `H` commit，再同步目标并更新 source baseline hash。
11. 同一个 contract test suite 必须能在源和目标两边运行；只证明目标测试通过不能证明两边一致。

## 7. M1：可靠性与低耦合改进

- [ ] `[P]` 增加 `logDebug()` 和 `HARNSS_EVENT_FULL=1` / `HARNSS_LOG_LEVEL=debug` 开关。
- [ ] `[P]` 默认不持久化 Claude、ACP、Codex 的完整高频事件。
- [ ] `[P]` 精确对齐字符串 2048、数组 100、对象 key 100、嵌套 8 和单行 64KB 限制及截断标记。

### 7.3 会话持久化

- [ ] `[P]` 将主 session JSON、`.meta.json` 和 metadata patch 改为同目录临时文件 + rename，精确保持源错误处理和清理语义。
- [ ] `[H]` 对同一会话路径建立串行写队列，防止较旧的异步写在较新写之后覆盖；同一实现同步到源、目标。
- [ ] `[H]` 处理 Windows 替换行为、临时文件清理和应用异常退出后的残留文件；同一实现同步到源、目标。

- OpenCode 可创建、发送、流式显示、中断、恢复、重启和删除。
- 多个 OpenCode session 不共享 cwd、端口、native session ID 或事件状态。
- 活动与后台 session 的工具、权限、用量和完成状态均可恢复。
- Split View 可发送、停止和切换 OpenCode 模型。
- 单元测试覆盖 binary lookup、model filter、adapter、usage 和 SSE retry。
- 至少用一个真实 provider 完成 Electron 端到端 smoke test。
- 失败场景矩阵覆盖：binary missing、auth/provider missing、start timeout、cancel start、process crash、SSE exhausted、send error、permission once/always/reject、resume missing ID。
- 连续创建/停止至少 20 个会话后，`sessions`、临时附件目录、端口监听、子进程和事件监听器均回到基线，不允许只验证 UI 消失。
- OpenCode 在最终验收构建中的入口和默认开关与源一致；临时 Developer Preview 不得成为关闭 parity 项的手段。

## 16. 回滚策略

- 每个工作包单独 commit，禁止把 OpenCode、Relay 和可靠性修改压成一个提交。
- 新持久化字段始终可选，回滚旧版应用后仍可读取普通会话。
- OpenCode 与 Relay 可在集成分支使用临时 Developer Preview 开关回滚，不通过删除 session 数据回滚；最终 parity baseline 不得只在目标保留该开关。
- 持久化改造发布前备份用户 session 目录，但不在正常启动时反复全量复制。
- 如虚拟滚动出现严重回归，可在集成分支保留临时 feature flag 回退到渐进渲染；关闭 parity 前必须删除旧路径，或把同一 flag 和默认值同步到两边。
- 回滚某个 `H` commit 时必须同时回滚源、目标；禁止让回滚本身重新制造双侧差异。

## 19. 保障结论与剩余边界

完成本次修订后，本计划可以在工程上对“功能一致”给出可审计保障：源行为有不可变基线，目标差异有逐项 ledger，超出源的加固必须双侧同步，最终由相同 contract、golden artifact 和零开放项门禁关闭。

计划仍不能替代外部依赖本身的稳定性。OpenCode provider、Codex app-server、操作系统进程/文件语义可能随版本变化，因此最终报告必须固定二进制版本、依赖版本和测试平台。未实际执行 M8、未完成真实 provider smoke test 或仍存在单侧 `H` 修改时，不得宣称两边功能一致。
